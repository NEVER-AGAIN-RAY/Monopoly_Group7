5. Functional requirements checklist
================================================================================

Core user requirements from teacher:
  - Support 2-5 players.
  - Allow AI opponents or real players.
  - GUI allows drawing cards, playing cards, paying rent, and managing properties.
  - Players can view public deck state, own assets, and opponents' public assets.
  - Hand cards remain private.
  - System automatically calculates rent, validates rules, and announces victory.
  - Save progress and restore later.

Startup and initialization:
  - HVM and PVP entry points.
  - HVM has Easy, Normal, Hard AI difficulty. Our project also has stronger/LLM modes;
    present these as enhancements, not as replacement for the required three.
  - 2-5 players for requirement compliance.
  - Standard Monopoly Deal deck configuration.
  - Initial deal of 5 cards per player.
  - Show deck remaining count and discard pile.
  - Rules panel available.

Turn logic:
  - At turn start, draw 2 cards.
  - If hand is empty before drawing, draw 5.
  - After drawing, player may perform up to 3 play actions.
  - Play actions include bank deposit, property deployment, and action execution.
  - End turn with hand <= 7; discard if above 7.

Rent/payment:
  - Rent calculated from property set progress, houses, hotels, and color rules.
  - Payment uses bank cards and property cards already on table.
  - Hand cards cannot directly pay.
  - No change is returned on overpayment.
  - If no payable table assets exist, current payment fails/no debt is carried.

Card legality:
  - Server validates illegal moves and invalid targets.
  - Examples: no rent without property color, exceeding 3 plays, invalid steal target.
  - Error messages should be clear in GUI.

Deck replenishment:
  - If draw pile is empty, reshuffle discard pile into draw pile.

Status feedback:
  - Current turn player.
  - Draw pile count and discard pile count.
  - Each player's hand count, properties, bank card count/value.
  - Opponents' public zones visible; opponent hand details hidden.
  - Text prompts and UI highlights for available actions.

Win/end:
  - Player wins after collecting 3 complete property sets.
  - Force termination after all quit or session timeout.

Save/pause:
  - HVM pause, continue, save/exit, abandon/exit.
  - Manual save and autosave every 3 full rounds.
  - Load game from local save.
  - PVP pause/load should use confirmation/vote behavior.

6. Non-functional requirements checklist
================================================================================

Usability:
  - GUI should be understandable for children aged 8+.
  - Legal/illegal actions should give feedback quickly, ideally within 0.5s.
  - Color property cards should include text labels for color-blind accessibility.
  - New-player guidance is desirable. If not fully implemented, use the rules/help panel
    and guided demo script as the practical evidence.

Performance:
  - AI decision + UI rendering target <= 1.5s.
  - Draw/shuffle/rent calculation target <= 0.3s.
  - Multiplayer should support up to 5 online players without obvious delay.
  - WebSocket sync target <= 200ms.
  - Evidence: PerformanceSmokeTest and manual demo responsiveness.

Reliability:
  - Invalid input cannot crash the program.
  - Autosave should remain valid through unexpected interruption.
  - Card count consistency should be protected.

Organizational requirements:
  - Java 17 or later.
  - JavaFX + FXML GUI.
  - Frontend/backend separation.
  - MVC architecture.
  - At least 5 design patterns.
  - Git collaboration with clear commit messages.
  - Cross-platform target: Windows/macOS/Linux.

Privacy/security:
  - Multiplayer players cannot access other players' hand details.
  - Save files can use optional AES-GCM via monopoly.saveKey.
