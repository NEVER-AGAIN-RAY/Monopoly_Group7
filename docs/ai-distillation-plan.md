# Monopoly Deal AI Distillation Plan

## Goal

Build an offline AI opponent for Monopoly Deal by distilling DeepSeek decisions into a small candidate-ranking model. The backend remains the authority for rules: every training row must come from a real `GameController` session, and every label must choose one candidate that the backend already proved legal.

For the current handoff status, artifact paths, and production completion gate, read `docs/ai-delivery-checklist.md` first.

## Current Pipeline

1. `SimulationBatchRunner` starts many independent `AI_VS_AI` games.
2. Each game owns its own `GameController` and isolated deck engine.
3. `BrokeredAiPlayStrategy` replaces the normal DeepSeek strategy during simulation.
4. The strategy asks the backend for legal candidates for these decision kinds:
   - `PLAY_CARD`
   - `JUST_SAY_NO`
   - `PAYMENT`
   - `OVERFLOW_DISCARD`
5. `DecisionBroker` collects decisions across games into micro-batches.
6. `DeepSeekBatchDecisionTeacher` can label a whole micro-batch with one DeepSeek request.
7. `JsonlDecisionTraceSink` writes one JSONL row per labeled decision.
8. `scripts/distill_dataset.py` validates JSONL, extracts candidate features, trains a PyTorch ranker, and reports metrics.
9. `LocalRankerAiPlayStrategy` loads the exported Java JSON model and ranks the same four decision kinds during backend gameplay.

The normal WebSocket server also supports multiple active `sessionId` values in one process. Each session maps to its own `GameController`; state broadcasts and private hand updates are scoped to the matching session connections. This is separate from the offline simulator, but it confirms that the backend architecture does not require one JVM per game.
Save/load votes are also session-scoped, so one busy backend can run many independent collection or play rooms without sharing pending confirmation state.

The batch teacher intentionally removes repeated stable prompt fields from each case and keeps shared strategy text once at the batch root. This keeps labels compatible with DeepSeek prompt caching and lowers per-case token cost.

When no paid teacher is used, `HeuristicDecisionTeacher` provides a deterministic no-cost baseline. `StrategicHeuristicDecisionTeacher` is the stronger no-key option for final local iteration: it uses board context, opponent complete-set pressure, payment preservation, and Just Say No thresholds while still choosing only backend-legal candidates. Both local teachers are useful for smoke tests and cheap pretraining, but production student models should still be trained and evaluated on `deepseek` rows.

## Dataset Contract

Each JSONL row uses schema `monopoly-deal-decision-v1`:

- `request.decisionId`: unique decision id.
- `request.sessionId`: source game.
- `request.actorPlayerId`: deciding player.
- `request.decisionKind`: decision type.
- `request.context`: compact public/private decision context.
- `request.candidates[]`: backend-generated legal options.
- `result.choiceId`: teacher-selected candidate id.

Quality gates:

- Schema must match.
- Candidate ids must be unique.
- `result.choiceId` must point to an existing candidate.
- Duplicate `decisionId` rows are rejected.
- Training splits are by `decisionId`, not by candidate row, so candidates from one decision never leak across train/validation.
- Default training splits are now by `sessionId`, which is stricter than decision-level splitting and avoids adjacent same-game states leaking into validation. Use `--split-by decision` only for quick debugging.
- `result.metadata.source` records whether a label came from `deepseek`, `local_heuristic`, `local_fallback`, or a DeepSeek parse fallback. Production training should prefer `deepseek` rows and separately report fallback rates.

## Training Target

The first production model is a candidate ranker, not a language model:

- Input: one `(state, candidate)` feature vector.
- Output: scalar score.
- Inference: score all backend-legal candidates and choose the highest.
- Loss: weighted binary cross entropy over teacher-positive vs teacher-negative candidates.
- Default balancing: `scripts/train_distilled_rankers.sh` enables decision-kind loss balancing for MLP and linear students. Rare kinds get a capped `sqrt(max_kind_count / kind_count)` multiplier, default cap `4.0`, so `JUST_SAY_NO`, `PAYMENT`, and `OVERFLOW_DISCARD` are not drowned by common `PLAY_CARD` rows. Set `MONOPOLY_TRAIN_BALANCE_BY_KIND=false` to disable this for ablations.
- Metrics:
  - Top-1 imitation accuracy by decision.
  - MRR by decision.
  - Top-1 by decision kind.

This matches the game architecture because the local model never invents actions; it only ranks legal choices generated by Java rules.

Two student formats are supported:

- PyTorch MLP (`candidate_ranker.pt`) plus Java-loadable JSON (`candidate_ranker_mlp.json`): stronger student for imitation metrics and usable by the Java backend.
- Linear JSON ranker (`candidate_ranker_linear.json`): weaker but pure-Java inference, used for Java battle smoke and integration tests.
- KNN nearest-neighbor baseline (`--model-type knn`): no Java runtime export, but useful as a non-neural offline comparison for reports and paper-style ablations.
- Forest-style bagged linear baseline (`--model-type forest`): no Java runtime export and no sklearn dependency; useful as a traditional model-family comparator alongside KNN.

Both Java formats are constrained to backend-generated legal candidates. In gameplay they rank `PLAY_CARD`, `PAYMENT`, `JUST_SAY_NO`, and `OVERFLOW_DISCARD`; if inference fails, the strategy falls back to the existing hard heuristic.

Batch collect with DeepSeek:

Set the key through `DEEPSEEK_API_KEY` or `-Dmonopoly.deepseek.apiKey=...`; no API key is stored in source.

```bash
mvn -q exec:java \
  -Dexec.mainClass=com.monopoly.tools.SimulationBatchRunner \
  -Dmonopoly.simulation.teacher=deepseek \
  -Dmonopoly.simulation.games=200 \
  -Dmonopoly.simulation.parallel=8 \

```

`monopoly.simulation.maxByKind` is optional. It prevents common `PLAY_CARD` rows from consuming the whole paid budget before rarer `JUST_SAY_NO`, `PAYMENT`, and `OVERFLOW_DISCARD` choices are collected. Quota-full decisions still get a local fallback so the simulated game can continue; they are just not recorded or sent to the paid teacher.

Trace output defaults to `fail_if_exists`. This is intentional: reusing a JSONL path with append semantics silently mixes old and new collection runs, corrupting quotas and source statistics. Use `-Dmonopoly.simulation.traceMode=append` only for an intentional resume, or `-Dmonopoly.simulation.traceMode=overwrite` for a deliberate replacement. The shell wrappers expose the same setting as `MONOPOLY_TRACE_MODE`.

Every full training run also writes `<output-prefix>-readiness.json`. This is the final handoff gate:

## Evaluation Plan

Offline evaluation:

- Dataset validity rate.
- Decision coverage by kind.
- Average candidates per decision.
- Top-1 imitation accuracy.
- MRR.
- First-candidate baseline and random expected top-1 baseline.
- Per-kind accuracy, especially `PAYMENT` and `JUST_SAY_NO`.

Gameplay evaluation:

- Use `LocalRankerAiPlayStrategy` for pure-Java inference from `candidate_ranker_mlp.json` or `candidate_ranker_linear.json`.
- Run round-robin AI battles:
  - distilled ranker vs Easy/Normal/Hard.
  - distilled ranker vs DeepSeek with small samples.
  - ablations by decision kind.
- Track natural win rate, winner distribution, average snapshots per game, force-end reasons, invalid action fallback count, payment overpay amount, complete-set tempo, and model latency.

## Research Direction

This project can be framed as rule-grounded teacher distillation for an imperfect-information card game:

- The legal-action generator is symbolic and exact.
- The teacher is a general LLM prompted with compact game context and strategy notes.
- The student is a cheap local ranker constrained to legal candidates.
- Evaluation can separate imitation quality from gameplay strength.

Related directions to cite and compare:

- DouZero highlights the same hard-card-game ingredients we face: imperfect information, multi-player interaction, large state/action spaces, and turn-dependent legal actions. It also validates action encoding plus parallel actors as a practical direction. Source: <https://arxiv.org/abs/2106.06135>
- Policy Distillation motivates compressing an expensive teacher policy into a smaller efficient student. Source: <https://arxiv.org/abs/1511.06295>
- DeepStack shows expert-level play in no-limit poker, an imperfect-information card game, and is useful comparison material for evaluation methodology. Source: <https://arxiv.org/abs/1701.01724>
- AlphaZero/MuZero-style work is useful as a contrast: strong game agents often combine legal action constraints, self-play, and policy/value learning, but Monopoly Deal has imperfect information and high stochasticity, so pure AlphaZero is not the first engineering target. Source: <https://www.nature.com/articles/s41586-020-03051-4>

Potential paper angle:

> LLM-labeled legal-action distillation for complex rule-based card games: using a symbolic engine to guarantee legal states/actions and a small local ranker to imitate high-cost teacher decisions.

Key experiments:

- Label efficiency: accuracy and win rate vs number of DeepSeek-labeled decisions.
- Batch labeling efficiency: cost and cache benefit vs batch size.
- Generalization: train on 2/3-player games, test on 4/5-player games.
- Decision-type ablation: only play-card labels vs all decision types.
- Teacher comparison: heuristic teacher vs DeepSeek teacher.
